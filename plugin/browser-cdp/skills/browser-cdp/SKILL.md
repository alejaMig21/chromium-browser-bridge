# browser-cdp

Same tools as the Claude in Chrome extension (`computer`, `navigate`, `read_page`, `find`, `form_input`, `get_page_text`, `javascript_tool`, `tabs_context_mcp`, `tabs_create_mcp`, `tabs_close_mcp`, `read_console_messages`, `read_network_requests`, `resize_window`, `file_upload`, `upload_image`, `gif_creator`, `browser_batch`), served by the `browser` MCP server. No extension and no Claude account are involved. The tool descriptions are the reference for every parameter; this skill is only the order of work.

1. **Browser first, and you own its lifecycle.** The page tools fail with "No browser is reachable" until one runs with a local debug port. Call `browser_launch` (`browser`: vivaldi by default, chrome, edge, brave; `headless`; `port`) yourself; never ask the user to start it. It opens a dedicated profile, so the user signs in once per site there; their everyday profile is not reachable. `browser_status` tells you what is running. When tools hang or error unexpectedly, call `browser_reconnect` (it leaves a healthy connection alone, repairs a broken one and restarts a browser this tool launched if it is dead). A browser this tool launched is also closed on its own after 10 minutes without tool calls (`BROWSER_IDLE_MS`, 0 disables); when a call then says "No browser is reachable", just call `browser_launch` again. When the work is done, call `browser_close` (closes only a browser this tool launched; `keepBrowser: true` just disconnects). A browser the user started on their own is never restarted or closed.

   **The user's own open browser** (they mention a page or tab they already have open, or want their real logins): call `browser_attach`. It needs the "Local Browser Bridge" extension loaded once in that browser; if it answers that no browser is connected, relay its install guide to the user word for word and retry. Several browsers can be connected at once, and a session works in exactly one: the optional `browser` argument (`chrome`, `edge`, `vivaldi`...; a part of the name is enough) picks it, and the reply starts with `Browser: <name> (...)` saying which one it is and why. Without `browser` the order is: the only connected browser, else the system default browser if it is connected, else the call fails and lists the connected ones, so ask the user which one (or call `list_connected_browsers`, which shows name, program path, active tab title and whether a session uses it, and works before any attach). Two profiles of one browser appear as `chrome-3f9a`. Calling `browser_attach` with another `browser` switches this session and releases its tabs in the first one. If the browser goes away the next call says `<name> disconnected. Still connected: ...`; attach again. Never fall back to `browser_launch` for this: that opens a different, empty profile. Calling `browser_attach` again while attached changes nothing: it names the work tab (`Tab ID N`) and keeps your tab numbers, which also survive a reconnect while the tab keeps its url. A tab the work tab opens (`target=_blank`, `window.open`) is yours at once and listed with its own id; `Unclaimed tab (browser tab N)` rows are tabs the user looked at that no session owns, not usable with `tabId`. While attached, the default tab is the one the user is looking at, their tabs are never navigated away or blanked, and `browser_close` only detaches.
2. **Look before acting.** Call `tabs_context_mcp` (with `createIfEmpty: true` when no tab exists), then `read_page` or `find` to get `ref_N` ids. Prefer refs over pixel coordinates; take a `screenshot` when layout matters. `read_page` also lists controls inside open shadow roots, shows `dialog "<name>"` nodes and starts with a `NOTE: modal dialog open` line when a modal blocks the page. Every `computer` action that acts (click, key, type, scroll, drag) ends with one line `focus: <role "name"> | dialog: <"name" or none> | url: <unchanged or the new url>`: read it instead of guessing whether a key or click landed.
   **Slow connection.** `navigate` answers as soon as the page starts to load, and a slow network can leave it empty for minutes. An empty read says `page empty: readyState=<x>, pending requests=<n>` (still loading, not blocked). Do not poll with `computer wait`: call `wait_for` with `text`, `selector` and/or `loaded: true` and a `timeout` of up to 300 seconds; it returns the moment the condition holds, or fails with the page state. `navigate` also takes `waitUntil` (`load`, `networkidle`) and `timeout` for the same reason.
3. **Respect the policy.** Navigation to internal schemes (`file:`, `chrome:`, `vivaldi:`), banks, payment, password-manager and `claude.ai` hosts is blocked, including redirects. Never try to route around a block: report it and ask the user. For a strict allowlist the user sets `allowedDomains` in `policy.json`.
4. **Ask before irreversible steps.** Submitting a form, buying, deleting or posting needs the user's explicit yes in chat.
5. **Recording.** `gif_creator` `start_recording`, do the steps, `stop_recording`, then `export`; the GIF is saved under the project `output/` folder and the path is returned.

Known limits: Vivaldi cannot create tabs over CDP (headless or not), so `tabs_create_mcp` fails fast there; work in the existing tab with `navigate`, or use `browser: "chrome"`, `"edge"` or `"brave"` when several tabs matter. Popups are disabled: `window.open` does nothing and `target=_blank` links open in the same tab. There is no per-site permission prompt and no tab group, unlike the extension.

Attached to the user's own browser: a screenshot never activates a tab or restores a window, so the user is not interrupted. It is the whole viewport, and a tab nobody is looking at (background tab, covered or minimized window) is woken with tiny captures, the way the official Claude extension does it; that takes about 4 seconds. On Chrome and Edge this works every time; on Vivaldi it is intermittent while the window is covered or minimized, and then the capture fails with a plain message that says why. `BROWSER_REVEAL_TABS=1` adds a last resort that shows the tab for a moment (it flickers, no focus is taken). Raw CDP errors such as "Only screenshots from surface are allowed" are never the user's fault or a permission-mode limit; read the page with `get_page_text` instead. While the debugger is attached the browser marks the tab as being debugged. Before you ask the user to click something themselves, call `browser_close` with `keepBrowser: true` so their tab is released (`browser_status` shows `debuggerAttached`).
